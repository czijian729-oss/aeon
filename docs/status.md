## 重复派发：根因已确认（推翻上一轮的「提交竞态」假设）

同一 tick 内两个 `scheduler: cron` run 各派发了全部 5 个 cron skill，53 秒内启动 10 个 skill run。上一轮 heartbeat 将其归因为「第二个 run 读到了第一个 run 提交前的 `cron-state.json`（提交/读取竞态）」——**该假设已被证伪**。

**真实机制：`workflow_dispatch` 的 `ref` 在派发创建时被固化为一个 commit SHA。** 两次 tick 在数秒内先后创建，`ref: main` 被解析成**同一个** SHA `893f542`；`actions/checkout` 按该 SHA 显式 fetch（`+893f542…:refs/remotes/origin/main`），因此第二个 run 无论何时 checkout，读到的都是派发创建时刻的 `cron-state.json`。

**证据链（逐条可复核）：**

| # | 事实 | 来源 |
|---|------|------|
| 1 | run A `#36618469365` job 19:20:03→19:20:33；run B `#36618512759` job 19:20:36→19:21:26 —— **时间不重叠**，`concurrency: aeon-scheduler` 已生效 | run jobs API |
| 2 | 两个 run 的 `head_sha` **均为 `893f542`**，`ref=main`，`event=workflow_dispatch` | run API |
| 3 | run A 于 19:20:28 提交 `526fa48`，**19:20:30 推送成功**（`State committed on attempt 1`） | run A 日志 |
| 4 | run B 于 19:20:39 才 checkout —— 比 run A 的推送**晚 9 秒** —— 却仍拿到 `893f542` | run B checkout 日志 |
| 5 | run B 重试循环打印 `Updating 893f542..526fa48`，证实其 base 是旧 SHA | run B 日志 |
| 6 | 两个 run 读到的 `last_dispatch` 水位线均为 `2026-09-28T10:50:35Z`，故**匹配到完全相同的 5 个档期** | 两个 run 的 `Matched:` 行 |

**关键结论：`concurrency` 无法阻止重复派发** —— 串行化只保证两个 job 不同时运行，不会刷新已被固化在事件里的 SHA。债务台账模型「按精确档期锚定、不会重复触发」的前提是**读到的状态是当前的**，而派发时 SHA 固化恰好破坏了这个前提。

**这是复发形态，非首次。** 同型成对 tick 在历史中出现 3 次：`08-28 00:36:50 / 00:40:19`、`09-03 09:48:20 / 09:50:43`、`09-29 19:19:55 / 19:20:16`。

**建议修复（`scheduler.yml`，约 2 行）：** 在两个 job 之间的 `concurrency` 锁**内**、读取 `cron-state.json` **之前**，强制重新解析分支头，而不是使用 checkout 固化的 SHA：

```yaml
- name: Checkout repo
  uses: actions/checkout@v7
  with: { fetch-depth: 1, token: "${{ secrets.GH_GLOBAL || secrets.GITHUB_TOKEN }}" }

- name: Re-pin to live main (defeat dispatch-time SHA pinning)
  run: git fetch origin main --depth=1 && git reset --hard FETCH_HEAD
```

（`git reset --hard` 在此安全：checkout 后、任何写入前，工作区无本地修改。这样第二个 run 会读到第一个 run 已提交的 `last_dispatch` 水位线，`cron-due.sh` 自然返回 not-due。）

## Root cause（触发器：09-25 定位，本轮修正）

**调度器 workflow 从未被 cron 原生触发过。** `scheduler.yml` 声明的 `on: schedule: '*/5 * * * *'` 在 GitHub 侧无投递记录。

**修正**：上一版状态页称实际驱动来自外部 pinger 的 `repository_dispatch`（`cron-tick`）。本轮核查近 60 次 run 的 `event` 字段——**全部为 `workflow_dispatch`，无一为 `repository_dispatch`**。即 pinger 调用的是 workflow-dispatch API（`gh workflow run` 等价物），而非 `cron-tick` 事件。这一区别正是 SHA 固化的来源：`workflow_dispatch` 会在创建时把 `ref` 解析成 SHA，`repository_dispatch` 不会。

**二次放大 —— 补位窗口偏小。** `scripts/cron-due.sh` 默认 `CATCHUP_HOURS=6`，`scheduler.yml` 覆盖为 `12`。日级 skill 只有在 tick 回溯 12h 内命中其档期时才补派。这解释了 09-26 / 09-27 的全天无 run（期间无 tick）。
